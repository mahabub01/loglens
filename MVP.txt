# ১. প্রজেক্ট পরিচিতি

## ১.১ ভূমিকা

LogLens হলো Laravel-এর জন্য একটি Developer Monitoring ও Log Analyzer প্যাকেজ। এর মাধ্যমে একজন ডেভেলপার একটি গ্রাফিক্যাল ড্যাশবোর্ড থেকে Laravel application-এর log file, error, exception, HTTP request performance, database query activity, Apache server status এবং server resource usage পর্যবেক্ষণ করতে পারবেন।

প্যাকেজটি এমনভাবে তৈরি করতে হবে, যাতে monitoring করার জন্য application-এর ওপর অপ্রয়োজনীয় database query, database write অথবা অতিরিক্ত performance overhead তৈরি না হয়।

## ১.২ সমস্যার বিবরণ

একটি production Laravel application পরিচালনা করার সময় ডেভেলপারদের সাধারণত যেসব সমস্যার মুখোমুখি হতে হয়:

- `storage/logs` থেকে manually log file খুলে দেখতে হয়।
- বড় log file থেকে নির্দিষ্ট error খুঁজে বের করা কঠিন।
- একই error বারবার তৈরি হলে প্রকৃত সমস্যাটি শনাক্ত করা কঠিন।
- Apache server-এর বর্তমান অবস্থা Laravel dashboard থেকে দেখা যায় না।
- Database query performance আলাদাভাবে বিশ্লেষণ করতে হয়।
- Slow HTTP request ও database query-এর মধ্যে সম্পর্ক খুঁজে বের করা কঠিন।
- Log file বড় হয়ে server-এর disk space শেষ হয়ে যেতে পারে।
- Monitoring package নিজেই অতিরিক্ত query ও resource consumption তৈরি করতে পারে।

LogLens-এর উদ্দেশ্য হলো এসব সমস্যা একটি নিরাপদ ও lightweight dashboard-এর মাধ্যমে সমাধান করা।

## ১.৩ প্রজেক্টের উদ্দেশ্য

১. Laravel-এর অনুমোদিত log file-গুলো graphical interface-এ দেখানো।

# ৩. প্রধান Functional Requirements

## ৩.১ Dashboard

Dashboard-এ application-এর সামগ্রিক অবস্থা ও monitoring metrics দেখাতে হবে।

### প্রয়োজনীয় Metrics

- Application health status
- প্রতি সেকেন্ডে request সংখ্যা
- HTTP error rate
- Average response time
- p95 ও p99 response time
- মোট observed exception
- Error ও warning distribution
- Database query count ও duration
- Slow query count
- Apache busy ও idle workers
- CPU ও memory usage
- Disk utilization
- Queue ও failed job statistics
- সর্বশেষ সফল collection time
- Collector availability status

### Dashboard Controls

- Time range selection
- Environment selection
- Auto-refresh interval
- Live monitoring toggle
- Collector status indicator
- Configurable metric cards
- Desktop, tablet ও mobile responsive layout

শূন্য মান এবং data unavailable থাকার অবস্থা আলাদা করে দেখাতে হবে। কোনো metric পাওয়া না গেলে `N/A` দেখাতে হবে; ভুলভাবে `0` দেখানো যাবে না।

## ৩.২ Log File Browser

প্যাকেজটি Laravel-এর নির্ধারিত log directory-এর ফাইলগুলো প্রদর্শন করবে।

### ফিচার

- অনুমোদিত `.log` ফাইলের তালিকা।
- File size ও সর্বশেষ modification time।
- Filename search।
- Filename, size ও modification time অনুযায়ী sorting।
- নির্দিষ্ট file-এর log দেখা।
- Daily, single-file ও custom channel log format সমর্থন।
- File permission ও read error প্রদর্শন।
- অনুমোদিত file download।
- বড় ফাইলের জন্য bounded reading ও pagination।
- File growth ও disk usage analysis।

### Log Source Configuration

Default log source হবে application-এর `storage/logs` directory।

প্রয়োজনে Apache access log, Apache error log এবং অন্যান্য অনুমোদিত log source যোগ করা যাবে। External log source ডিফল্টভাবে read-only থাকবে।

User input-এর মাধ্যমে arbitrary filesystem path access করার সুযোগ দেওয়া যাবে না।

## ৩.৩ Log Parser

Parser-কে Laravel-এর প্রচলিত log format ও standard severity level সমর্থন করতে হবে।

### Severity Level

- Emergency
- Alert
- Critical
- Error
- Warning
- Notice
- Info
- Debug

### Parsing Requirements

- Timestamp, channel, severity ও message শনাক্ত করা।
- Exception class শনাক্ত করা।
- Multiline stack trace-কে সংশ্লিষ্ট log entry-এর সঙ্গে যুক্ত করা।
- Laravel daily log file সমর্থন করা।
- Malformed বা অসম্পূর্ণ log entry পরিচালনা করা।
- Parsing ব্যর্থ হলে মূল log content সংরক্ষণ করা।
- পুরো file memory-তে load না করা।

Application-specific log format-এর জন্য parser extensible হতে হবে।

## ৩.৪ Search ও Filtering

ব্যবহারকারী নিচের বিষয়গুলো দিয়ে log filter করতে পারবেন:

- Keyword
- Severity
- Date ও time range
- Log file
- Exception class
- Message text
- Request বা correlation ID, যদি উপলভ্য থাকে

Search-এর জন্য bounded file reading অথবা ঐচ্ছিক indexed backend ব্যবহার করতে হবে।

Filesystem-ভিত্তিক log search করার জন্য application database query চালানো যাবে না।

## ৩.৫ Error Grouping ও Analysis

একই ধরনের error-কে normalized error fingerprint ব্যবহার করে group করতে হবে।

### প্রয়োজনীয় ফিচার

- Error occurrence count
- প্রথমবার শনাক্ত হওয়ার সময়
- সর্বশেষ শনাক্ত হওয়ার সময়
- Error severity
- Exception class
- Sample message
- Stack trace preview
- Error frequency chart
- সবচেয়ে বেশি হওয়া error
- নতুন শনাক্ত হওয়া error
- দ্রুত বাড়তে থাকা error
- Slow request-এর সঙ্গে সম্ভাব্য সম্পর্ক

Fingerprint তৈরি করার সময় sensitive data বাদ দিতে হবে।

শুধু message দেখতে একই রকম হলেই দুটি error-কে একই error বলা যাবে না। Exception type ও normalized message বিবেচনা করে configurable fingerprinting করতে হবে।

## ৩.৬ Live Log Tail

নতুন log entry আসার সঙ্গে সঙ্গে তা দেখার ব্যবস্থা থাকতে হবে।

### Requirements

- Incremental file reading।
- নির্দিষ্ট log file নির্বাচন।
- Pause ও resume control।
- Severity filter।
- প্রয়োজন অনুযায়ী নতুন entry-তে auto-scroll।
- Connection failure হলে নিরাপদে reconnect।
- প্রতিবার পুরো log file পুনরায় পাঠানো যাবে না।

প্রাথমিক সংস্করণে file offset ব্যবহার করে incremental polling করা যেতে পারে। ভবিষ্যতে ঐচ্ছিক Server-Sent Events যোগ করা যাবে।

## ৩.৭ Log Cleanup ও Retention

### Manual Operations

- নির্দিষ্ট log file clear করা।
- নির্বাচিত একাধিক file clear করা।
- Log file archive করা।
- Log file download করা।
- Cleanup-এর আগে preview দেখানো।
- প্রতিটি operation-এর ফলাফল দেখানো।

### Automatic Retention

- Log retention period নির্ধারণ।
- পুরোনো log file শনাক্ত করা।
- ঐচ্ছিক archive।
- Maximum file size ও disk usage threshold।
- Laravel Scheduler অথবা নির্দিষ্ট CLI command দিয়ে maintenance।

### নিরাপত্তা

- Cleanup-এর জন্য উপযুক্ত authorization বাধ্যতামূলক।
- Destructive action-এ confirmation থাকতে হবে।
- Dry-run mode থাকতে হবে।
- অনুমোদিত directory-এর বাইরের file delete করা যাবে না।
- Path traversal ও অননুমোদিত symbolic link প্রত্যাখ্যান করতে হবে।
- Active log file নিরাপদভাবে পরিচালনা করতে হবে।
- Audit mechanism সক্রিয় থাকলে cleanup action-এর history সংরক্ষণ করতে হবে।

Explicit retention policy configure না করা পর্যন্ত automatic log deletion চালু করা যাবে না।

# ৪. Apache Server Monitoring

## ৪.১ উদ্দেশ্য

Laravel dashboard থেকে Apache web server-এর status ও performance metrics পর্যবেক্ষণ করা।

## ৪.২ প্রয়োজনীয় Metrics

- Apache uptime
- Total accesses
- Total transferred bytes
- Requests per second
- Bytes transferred per second
- Busy workers
- Idle workers
- Scoreboard state
- Apache service availability
- Access log থেকে response code distribution
- Access log-এ timing data থাকলে request latency

## ৪.৩ Apache Integration

প্রধান integration হিসেবে Apache-এর `mod_status` module এবং machine-readable status endpoint ব্যবহার করা হবে।

উদাহরণ:

`http://127.0.0.1/server-status?auto`

এটি একটি উদাহরণ URL। প্রকৃত server configuration অনুযায়ী URL পরিবর্তন করতে হবে।

### নিরাপত্তা

- Status endpoint শুধু localhost অথবা অনুমোদিত monitoring process-এর জন্য উন্মুক্ত রাখতে হবে।
- Public internet থেকে unrestricted access বন্ধ রাখতে হবে।
- Server credential browser-accessible configuration-এ রাখা যাবে না।
- Dashboard user-কে arbitrary URL সরবরাহ করতে দেওয়া যাবে না।
- Connection timeout ও error handling থাকতে হবে।
- Apache status configure করা না থাকলে collector বন্ধ থাকবে।

## ৪.৪ প্রতি সেকেন্ডে Collection

লক্ষ্য হবে প্রতি এক সেকেন্ডে metrics সংগ্রহ করা।

নিচের বিষয়গুলো আলাদা রাখতে হবে:

- Metrics collection interval
- Browser refresh interval
- Metrics aggregation interval

একটি shared collector নির্দিষ্ট interval-এ metrics সংগ্রহ করবে। একাধিক dashboard visitor-এর জন্য আলাদা Apache polling চালানো যাবে না।

একটি long-running collector process ব্যবহার করা যেতে পারে। শুধু প্রতি মিনিটে Laravel Scheduler চালিয়ে প্রতি সেকেন্ডে collection নিশ্চিত করা সম্ভব নয়।

### Rate Calculation

Apache-এর counter cumulative হয়। পরপর দুটি reading থেকে rate হিসাব করতে হবে।

`Requests per second = (বর্তমান total accesses - পূর্ববর্তী total accesses) / অতিবাহিত সময়`

Transferred bytes-এর ক্ষেত্রেও একই পদ্ধতি ব্যবহার করতে হবে।

Counter reset, Apache restart, unavailable reading এবং negative delta সঠিকভাবে পরিচালনা করতে হবে।

পূর্ববর্তী reading না থাকলে অথবা counter reset হলে নতুন valid baseline পাওয়া পর্যন্ত rate unavailable হিসেবে দেখাতে হবে।

## ৪.৫ Apache Monitoring-এর সীমাবদ্ধতা

Apache `mod_status` সরাসরি সব application-level metric সরবরাহ করে না।

Route-level response time, Laravel exception এবং database query activity জানার জন্য Laravel instrumentation অথবা অতিরিক্ত access-log parsing প্রয়োজন হবে।

কোন metric Apache থেকে এসেছে এবং কোন metric অন্য collector থেকে এসেছে, তা documentation-এ স্পষ্ট করতে হবে।

# ৫. অতিরিক্ত Database Query ছাড়াই Database Monitoring

## ৫.১ মূল Requirement

Monitoring metrics সংগ্রহ করার জন্য default mode-এ application database-এ অতিরিক্ত query চালানো যাবে না।

Monitoring-এর জন্য বাধ্যতামূলক database table তৈরি করা বা প্রতিটি query event-এর জন্য database insert করা যাবে না।

## ৫.২ Existing Query Observation

Laravel-এর বিদ্যমান database query event পর্যবেক্ষণ করতে `DB::listen()` ব্যবহার করা যেতে পারে।

প্রতিটি observed query থেকে নিচের তথ্য সংগ্রহ করা যেতে পারে:

- Query execution duration
- Query count
- Connection name
- Request correlation ID
- Slow query count
- Aggregated query duration
- ঐচ্ছিক normalized query fingerprint

Query listener-এর ভেতর থেকে monitoring-এর জন্য আরেকটি database query চালানো যাবে না।

## ৫.৩ Query Aggregation

Query metrics memory-তে aggregate করতে হবে।

উদাহরণ:

- Observed query count: 32
- Aggregate query duration: 84 ms
- Slow query count: 2
- Connection: mysql

এগুলো শুধু উদাহরণ।

Database driver যে execution duration প্রদান করে, তার সীমাবদ্ধতা documentation-এ উল্লেখ করতে হবে। Connection establishment এবং অন্যান্য client-side overhead ওই duration-এর মধ্যে অন্তর্ভুক্ত কি না, তা স্পষ্ট করতে হবে।

## ৫.৪ N+1 Query Detection

একটি request-এর মধ্যে repeated normalized query pattern বিশ্লেষণ করে সম্ভাব্য N+1 সমস্যা শনাক্ত করা যেতে পারে।

Report-এ থাকবে:

- Repeated query pattern
- Repetition count
- সংশ্লিষ্ট request বা route
- মোট observed query duration
- সম্ভাব্য optimization suggestion

এটি heuristic হিসেবে কাজ করবে; সব N+1 সমস্যা শনাক্ত করার নিশ্চয়তা দেওয়া যাবে না।

## ৫.৫ Database Server Metrics

Active connection, lock wait, buffer pool statistics ও global status-এর মতো server-level metrics পেতে আলাদা instrumentation প্রয়োজন হতে পারে।

Strict zero-extra-query mode-এ প্রতি request বা dashboard refresh-এ নতুন monitoring SQL চালিয়ে এসব metrics সংগ্রহ করা যাবে না।

ঐচ্ছিক integration হিসেবে ব্যবহার করা যেতে পারে:

- Existing database exporter
- External monitoring agent
- আলাদা scheduled collector
- Explicitly enabled, rate-limited database health probe

Optional probe চালু থাকলে তা স্পষ্টভাবে জানাতে হবে। Strict mode-এ এটি default-ভাবে বন্ধ থাকবে।

## ৫.৬ Query Data Privacy

ডিফল্টভাবে:

- Raw query binding সংগ্রহ করা যাবে না।
- Password, token ও sensitive parameter value সংরক্ষণ করা যাবে না।
- SQL statement সংরক্ষণ ঐচ্ছিক রাখতে হবে।
- Sensitive field redaction-এর ব্যবস্থা থাকতে হবে।
- Query fingerprint-এর memory consumption সীমাবদ্ধ রাখতে হবে।
- Detailed query observation বন্ধ করার configuration থাকতে হবে।

# ১১. Metrics Storage Strategy

## ১১.১ Default Mode

Default mode-এ filesystem-based log analysis ও in-memory metrics aggregation চলবে। কোনো বাধ্যতামূলক database schema প্রয়োজন হবে না।

## ১১.২ Storage Options

### In-memory Storage

ব্যবহার উপযোগী:

- Request-level metrics
- স্বল্পমেয়াদি aggregation
- Local development
- Single-process monitoring

সীমাবদ্ধতা: Process restart হলে metrics হারিয়ে যেতে পারে এবং একাধিক PHP worker-এর মধ্যে data share নাও হতে পারে।

### Shared External Storage

ঐচ্ছিক Redis বা অন্য shared backend ব্যবহার করা যেতে পারে:

- Cross-worker counter
- Shared collector state
- স্বল্পমেয়াদি time series
- Distributed application instance

### Historical Metrics

দীর্ঘমেয়াদি history রাখতে হলে কোথাও persistent storage প্রয়োজন।

Application database-এ monitoring query না চালিয়ে optional storage adapter-এর মাধ্যমে এই সুবিধা দিতে হবে।

Strict no-extra-database-query mode সবসময় উপলভ্য থাকতে হবে।

# ১৪. Security Requirements

Application log-এ sensitive information থাকতে পারে। তাই security বাধ্যতামূলক।

## ১৪.১ Authentication ও Authorization

- Default-ভাবে authenticated access বাধ্যতামূলক।
- Permission-based access control সমর্থন।
- Log view ও cleanup permission আলাদা করা।
- Configuration পরিবর্তনের জন্য administrator permission।
- Laravel Gate বা Policy integration সমর্থন।

## ১৪.২ Filesystem Security

- অনুমোদিত directory-এর মধ্যে access সীমাবদ্ধ রাখা।
- Path canonicalization ও validation।
- Path traversal প্রতিরোধ।
- অননুমোদিত symbolic link প্রত্যাখ্যান।
- Arbitrary file read/delete বন্ধ রাখা।
- Least-privilege filesystem permission ব্যবহার।
- `chmod -R 777` ব্যবহার বাধ্যতামূলক করা যাবে না।

## ১৪.৩ Data Protection

- Credential ও sensitive value redact করা।
- SQL binding প্রকাশ না করা।
- Download করা log file সুরক্ষিত রাখা।
- Private log content public cache-এ রাখা যাবে না।
- Unauthorized user-কে internal stack trace দেখানো যাবে না।
- উপযুক্ত HTTP response header ব্যবহার।
- Public access থেকে Apache status endpoint সুরক্ষিত রাখা।

## ১৪.৪ Operational Safety

- Cleanup-এর আগে explicit confirmation।
- Dry-run cleanup।
- Concurrent file write নিরাপদভাবে পরিচালনা।
- Privileged action-এর audit history, যদি enabled থাকে।
- Collector unavailable হলে safe fallback।
- Dashboard input থেকে arbitrary shell command বা SQL execute না করা।

## ১৫.১ বাধ্যতামূলক নীতি

- Metrics memory সীমাহীনভাবে বাড়তে দেওয়া যাবে না।

- Apache collector প্রতি সেকেন্ডে collection করার চেষ্টা করবে।
- Collector timeout-এর পর request অনির্দিষ্টকাল আটকে থাকবে না।
- Metrics buffer-এর size ও retention configurable হবে।

Testing-এর সময় package-এর CPU, memory এবং latency overhead পরিমাপ করতে হবে।

# ১৬. Error Handling ও Package Observability

প্যাকেজটির নিজস্ব monitoring status-ও পর্যবেক্ষণ করতে হবে।

# ১৯. Acceptance Criteria

প্রথম production-ready release সম্পূর্ণ বলে বিবেচিত হবে যখন:

১. Laravel 12 application-এ প্যাকেজটি install করা যাবে।

২. Dashboard-এ অনুমোদিত log file দেখা যাবে।

৩. বড় log file পুরো memory-তে load না করে search ও view করা যাবে।

৪. Severity filter ও error grouping সঠিকভাবে কাজ করবে।

৫. Log cleanup শুধু অনুমোদিত user ও অনুমোদিত file-এর জন্য কাজ করবে।

৬. Database observer কোনো monitoring SQL execute না করে existing query metrics সংগ্রহ করবে।

৭. Middleware enabled থাকলে HTTP performance metrics পাওয়া যাবে।

৮. Supported server-এ configured interval অনুযায়ী Apache metrics সংগ্রহ করা যাবে।

৯. Dashboard missing বা stale metrics সঠিকভাবে দেখাবে।

১০. Core functionality ও security-এর জন্য automated test থাকবে।

১১. Monitoring failure-এর কারণে মূল application crash করবে না।

১২. Strict monitoring mode-এ application database migration প্রয়োজন হবে না।

১৩. Production installation guide-এ প্রয়োজনীয় permission ও collector setup ব্যাখ্যা করা থাকবে।

১৪. সব destructive operation-এ উপযুক্ত safeguard থাকবে।

১৫. Performance test-এ bounded memory use ও গ্রহণযোগ্য overhead প্রমাণিত হবে।

# ২১. চূড়ান্ত Product Definition

LogLens হবে একটি lightweight Laravel developer observability package, যার তিনটি প্রধান capability থাকবে।

## ১. Log Analyzer

Graphical log browsing, searching, filtering, error grouping এবং safe cleanup।

## ২. Live Performance Monitor

HTTP request metrics, response time এবং বিদ্যমান database query activity পর্যবেক্ষণ—Strict mode-এ অতিরিক্ত monitoring SQL ছাড়াই।

## ৩. Server Monitor

Apache status, worker utilization, system resources এবং ঐচ্ছিক queue ও scheduler integration।

প্যাকেজটির মূল অগ্রাধিকার হবে:

- নিরাপত্তা
- সীমিত resource consumption
- Modular architecture
- Predictable monitoring overhead
- Zero-extra-database-query mode
- Production-ready implementation

প্রথম release-এ নির্ভরযোগ্য Log Analyzer এবং zero-extra-query monitoring architecture-কে অগ্রাধিকার দিতে হবে। এরপর Apache, system metrics, historical storage ও advanced alerting আলাদা module হিসেবে যোগ করা উচিত।

এই ডকুমেন্টে প্যাকেজটির প্রয়োজনীয়তা ও technical design নির্ধারণ করা হয়েছে। Production-ready হওয়ার জন্য বাস্তব implementation, integration test, performance benchmark এবং security validation সম্পন্ন করতে হবে।
